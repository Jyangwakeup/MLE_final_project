## 结论与优先级

先修复训练回调破坏自身炸弹责任状态的问题，再原样复测 r7 套餐。当前结果不能被解释为正确实现的 v5 训练已经达到算法上限。冻结确认失败仍然有效，不将失败重新解释为通过。

修复后若仍有瓶颈，按证据分别做奖励目标对齐和 Task 2 Replay 保留消融；不要同时改变奖励、Replay、特征和训练长度。三个训练种子共同通过独立确认、唯一候选通过主验证，仍是当前内部晋级标准。课程的 Task 3 学习目标与团队的数值门槛须区分，见 [课程要求](../../PROJECT_REQUIREMENTS.md) 与 [当前实验合同](../../experiments/task3_plateau_stopping.json)。

## 新发现：训练回调清掉自身炸弹责任

相关代码：

- [action_history.py](../../agent_code/learning_common/action_history.py)：`action_history_for_state` 在传入状态 `self[2] == True` 时清空自身炸弹位置和 pending；`own_bomb_history_for_state` 会调用它。
- [callbacks.py](../../agent_code/double_dqn_continuous_v2_agent/callbacks.py)：选择 BOMB 后 `record_selected_action` 记录 pending；探索和贪心都从安全掩码中选动作。
- [train.py](../../agent_code/double_dqn_continuous_v2_agent/train.py)：`_transition` 无条件用放弹前 `old_state` 调用 `own_bomb_history_for_state`。这个旧状态仍能放弹，因此清掉了刚记录的责任；后续新状态读取无法恢复位置。

最小只读复现：构造已记录 pending=True 的 owner，依次读取放弹前 `self[2]=True` 状态和放弹后 `self[2]=False`、含自身炸弹的状态，输出 pending 从 True→False，新状态返回 position=None、visible=False、timer=None。即使旧特征缓存命中，`_transition` 的直接历史调用仍触发问题。

实际证据：[seed 22 c0150 timing](../../runs/task3_plateau_ddqn_cv2_r7_s22_c0150_79d1e87/timing.jsonl)，第106局：259步 BOMB 获放行；260步开始 pending=False、visible=False；262/263步退回物理动作；[episodes](../../runs/task3_plateau_ddqn_cv2_r7_s22_c0150_79d1e87/episodes.jsonl) 记263步死于自己的炸弹。

对三份已选 checkpoint 对应的50局训练日志，统计同一局连续步中 BOMB 后下一次 act：

| 日志 | 可配对 BOMB→下一步次数 | 下一步 pending=False |
|---|---:|---:|
| seed 11 c0150 | 2281 | 2281 |
| seed 22 c0150 | 2274 | 2274 |
| seed 33 c0050 | 2331 | 2331 |

这是已选动作日志统计，不单独证明每次 BOMB 都成功放置；上述自炸实例与源码链条独立支持生命周期缺陷。

汇总有效 `79d1e87` 训练子 run 的 episodes：seed 11 自杀52/250（20.8%），seed 22 为64/250（25.6%），seed 33 为29/150（19.3%）；冻结确认三者自杀均0/20。训练中 guarantee-loss、search-timeout、avoidable-collapse 计数为0，不能据此宣称安全责任正常：责任状态已经消失，而且 v1→physical fallback 本身也不一定计作 guarantee-loss。不能把全部训练自杀或确认失败归因于该缺陷，尚需修复后的对照实验。

### 修复与验证建议

1. 将实时历史推进与读取旧状态分离；历史快照不得因 replay/transition 构建回退。保证旧状态特征对应动作前历史，新状态与下一次 act 看到动作后历史。
2. 回归测试必须包含实际 `act(BOMB) → game_events_occurred → 下一次act` 调用链、连续多步责任、火焰消失后解除、回合重置及恢复；同时验证 next-state bootstrap mask 与推理 mask 一致。只测安全搜索纯函数不够。
3. 使用已有开发/训练场景做短程探索诊断，检查训练中责任真实存续、回退原因与自杀轨迹；不得用最终保留测试集调试。
4. 修复会改变动作与训练分布。从各自 Task 2 父 run 重建 Task 3 实验，不从受影响的 Task 3 replay 继续。显式记录新源码/恢复协议血缘，不覆盖旧证据。
5. 第一轮仅修正生命周期，保持 DDQN、84维、r7、n-step5、对手、75%父任务Replay和平台早停规则，隔离正确性修复的收益。旧 Task 2 权重保留，但对修复后运行合同重做必要的保留/安全检查。

## 修复后的学习瓶颈与独立消融

更详细的源码机制审阅见 [机制笔记](task3-learning-mechanisms-review.md)。

### 奖励目标

[r7定义](../../agent_code/team_agent/rewards.py) 中 coin=3、kill=5，且有实际炸箱+0.2和安全放弹预测炸箱收益（最多+0.6）。官方 coin=1、kill=5。r7 的直接事件奖励把一次击杀折合约1.67枚金币，官方为5枚；这与资源提升而战斗改善不稳定一致，但目前不构成单独因果证明。

若正确性修复后仍为主要瓶颈，建议预注册一个单变量候选：coin维持3，kill由5改15，其他条目先固定。它只对齐金币/击杀比例，不等于整个奖励函数变成官方得分；更大Q目标可能影响共享表示与保留，必须测量。需新 reward ID 和显式迁移：从 Task 2 父模型开始；Task1/2没有击杀事件且其他奖励不变时旧 parent replay 才能证明数值兼容。旧 Task3 n-step 奖励已聚合，不能混入新任务缓存或靠改标签重解释。

### Replay 与 Task 2 保留

当前batch64的75% parent约为Task1/2各24行、Task3为16行，并非Task1/2/3=16/32/16。teacher已正确为直接Task2 parent，不能再次将它作为待修根因。若修复后仅Task2保留不足，则独立比较16/32/16，将已达50分的Task1部分预算移给Task2，保持Task3份额不变；这只是有依据的候选，不能保证解决遗忘。[ADR0005](../adr/0005-stop-at-the-earliest-retaining-task3-checkpoint.md)已有相关设计，但原先启用条件不同，新一轮应另行记录合同。

若战斗经验覆盖不足，再考虑Task3内部按炸弹周期/战斗事件分层，并检查采样偏差。不要直接提高Task3总份额，加剧旧任务保留风险。优先经验回放方法来源：[Schaul et al., 2015](https://arxiv.org/abs/1511.05952)，并不代表该方法在本项目已经验证有效。

### 行为与特征

确认原始episodes显示seed22的连续WAIT≥10步局数由5/20增至16/20；WAIT步数由1879/8000增至2962/8000。其中2607次WAIT在诊断中归于无可达金币。seed33长WAIT局由1/20增至5/20。该信号提示缺少资源后可能没有有效战斗行为，不能据此给所有WAIT加惩罚，等待也可能是正确逃生动作。

按episode死亡归因统计，候选11/22/33对coin_collector_agent击杀分别为3/20、1/20、0/20；对peaceful_agent为7/20、6/20、6/20。需在开发集记录：敌人在场且无金币时的行为、可安全放弹的战斗机会、Q是否偏好WAIT、放弹是否被安全约束否决。只有证明84维无法区分关键局面后，再增加客观敌距、通路/敌方可达空间等特征；不写追敌方向或最佳动作规则。
