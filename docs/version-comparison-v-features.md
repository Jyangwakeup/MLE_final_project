# V 版本对比：连续特征表示的演进

## 1. 范围与读法

本文中的 `v` 专指 `agent_code/team_agent/feature_system/` 中注册的连续向量特征版本，而不是 Agent 目录名中的实验包装版本。当前主线包括 `continuous-v1` 至 `continuous-v11`；其中 v6 以后使用更具语义的正式 ID。

需要先强调：这不是一条完整的线性链。v1→v8 基本是逐步追加；v9 是对 v8 的压缩投影；v10 和 v11 都从 v7 分叉，而不是建立在 v9 或彼此之上。

```text
v1 (70)
└─ v2 (84)
   └─ v3 (107)
      └─ v4 (126)
         └─ v5 (140)
            └─ v6 (160)
               └─ v7 (162)
                  ├─ v8 (163) ─ v9 (139，压缩 v8)
                  ├─ v10 (170，象限密度分支)
                  └─ v11 (170，可达箱子目标分支)
```

维数均来自运行时注册表的 schema，而不是根据文件名猜测。

## 2. 所有版本的共同点

- 都输出固定长度 `float32` 向量，并携带相同动作顺序下的物理合法动作掩码。
- 动作顺序由共享 `ACTIONS` 定义，版本升级不能偷偷改变动作索引，否则旧 checkpoint 的输出头将失去含义。
- 特征只描述状态、候选动作后果或历史事实；最终动作仍由学习模型的 Q 值选择。
- 距离、计数、时间和面积一般归一化到有限范围，以避免不同量纲直接支配网络。
- 每个版本都有显式 `feature_id`、字段顺序、向量形状和 normalization 契约。新 checkpoint 会校验这些内容，因此不同维数或字段顺序不能当作“同一模型”直接恢复。
- v2 以后逐渐引入 episode 内历史状态，因此抽取特征时必须传入与实际决策对应的历史快照；不能用当前可变历史重建旧 transition。
- 特征版本、奖励版本和 mask 版本相互独立。例如 `continuous-v5 + r18 + mask-v5` 是一个组合，不表示三者的数字必须相同。

## 4. 逐版本细节

### 4.1 v1：70 维连续基础表示

v1 为六个候选动作各生成 10 个特征，共 60 维：

1. `legal`：动作在碰撞、占用和放弹资格意义上是否合法。
2. `danger_t1/t2/t3`：执行该动作后目标格在未来第 1/2/3 步是否危险。
3. `earliest_danger`：最早危险时间，按预测 horizon 归一化；完整 horizon 内无危险记为 1。
4. `safe_horizon`：从该动作开始最多能存活到预测 horizon 的哪一步。
5. `safe_area`：预测末端安全前沿大小除以棋盘面积。
6. `coin_distance_delta`：动作前后到金币目标的距离改善量。
7. `crate_frontier_distance_delta`：到可炸箱子前沿的距离改善量。
8. `opponent_distance_delta`：到对手的距离改善量。

另有 10 个全局特征：是否存在可达金币/箱子前沿/对手，当前能否放弹，放弹后能否活过 horizon，放弹后的安全面积，爆炸范围中的箱子数与对手数，存活对手比例，以及回合进度。

因此 v1 已经具备“资源导航 + 对手接近 + 炸弹后果 + 时间危险”的完整基础，但没有跨步记忆，无法直接识别来回走或目标是否连续。

### 4.2 v2：在 v1 上增加 14 维历史信息

新增内容为：

- 7 维上一动作 one-hot：六个动作加 `none`，用于回合首步或未知历史。
- 1 维 `coin_target_continues`：确定性 BFS 选出的金币目标是否与上一决策一致。
- 6 维 `returns_previous_position`：每个候选动作是否会立即回到上一位置。

这使模型能区分“同一个静态局面下继续朝目标前进”和“刚走一步又折返”。它仍保留 v1 的前 70 维语义，因此可通过复制旧输入列进行受控扩展，但直接加载 70 维网络仍不兼容。

仓库还保留 `continuous-v2-legacy78` 兼容版本；它是历史 checkpoint 兼容入口，不属于当前 v1–v11 主演进链，不能与正式 84 维 v2 混用。

### 4.3 v3：在 v2 上增加 23 维显式安全信息

每个动作新增 3 项，共 18 维：

- `survives_horizon`：该物理合法动作是否能活过 H=7。
- `escape_slack`：危险截止时间减去最短逃逸步数后的归一化余量。
- `safe_second_action_fraction`：下一步仍可生存的分支数占 5 个位置动作的比例。

再增加 5 个全局己方炸弹事实：安全动作比例、己方炸弹义务是否存在、炸弹是否仍可见、倒计时比例、Agent 是否位于己方炸弹火力线上。

此外，v3 将继承字段中的 `safe_area` 从线性面积比例改为 `log1p(area)/log1p(board area)`。所以 v3 不只是尾部追加：即使前缀字段名相同，安全面积的数值尺度也发生变化。

### 4.4 v4：在 v3 上增加 19 维有界循环历史

新增 1 个全局 `wait_streak`，使用 `log1p(min(streak,8))/log1p(8)`；每个动作再增加：

- 是否回访近期位置；
- 候选动作闭合的周期长度，检测 2–8 步周期；
- 完整周期重复次数，最多截断为 4 次。

这里的循环检测不是只比较端点：继续重复必须让完整中间位置块相同，减少把正常绕障误判为周期。v4 让奖励 r10 一类的“有界历史反循环惩罚”有可观察依据，也让模型自己学习何时 WAIT 或回访是合理的。

### 4.5 v5：在 v4 上增加 14 维全局炸箱目标上下文

每个动作新增两项，共 12 维：

- `crate_half_plane_density`：动作面对半平面中的箱子占全部箱子的比例；
- `bomb_objective_distance_delta`：动作后到已保存放弹目标的距离改善。

另加：

- `crate_fraction`：剩余箱子占棋盘面积比例；
- `bomb_objective_active`：是否存在跨步保留的放弹后箱子前沿目标。

v5 解决的是局部距离无法表达的全局方向和“放完弹后还要继续完成哪个资源目标”。这要求 Agent 维护 bomb objective 历史，因而 transition 重建尤其需要使用决策快照。

### 4.6 v6：在 v5 上增加 20 维对手跟踪

正式 ID 是 `continuous-v6-opponent-tracking`。它选择并跨步保持一个对手目标。

每个动作新增两项，共 12 维：到被跟踪对手的距离变化，以及动作后是否与该对手形成炸弹火力线。另有 8 个全局项：目标是否存在、是否与上一状态为同名目标、归一化距离、相对 x/y、观测到的一步运动 x/y、以及目标周围可用移动格加 WAIT 占 5 的比例。

共同目的不是直接指定追击动作，而是让网络区分：目标在哪、正往哪走、是否容易逃、当前动作是否改善施压位置。

### 4.7 v7：在 v6 上增加 2 维可观察击杀阶段

正式 ID 是 `continuous-v7-phase-aware`。新增：

- `own_kills_fraction`：本局己方击杀数截断到 3 后除以 3；
- `own_kill_achieved`：是否已经至少击杀一名对手。

它为 r21/r22 的击杀前后奖励权重切换提供明确、可观察的状态，而不是按固定回合数猜测“阶段”。

### 4.8 v8：在 v7 上增加 1 维安全炸箱机会

正式 ID 是 `continuous-v8-safe-crate-opportunity`。唯一新增字段 `survivable_crate_bomb_utility` 同时要求当前放弹能影响箱子且放弹后仍可在预测 horizon 内存活。它把“可炸到箱子”和“能安全撤离”组合成一个直接交互量，便于模型识别值得放弹的资源机会。

它仍是事实特征，不会强制选择 BOMB；真正的动作排序仍由 Q 网络完成。

### 4.9 v9：从 v8 压缩到 139 维

正式 ID 是 `continuous-v9-compact`。它不新增游戏信息，而是从 v8 删除 24 个字段：20 个结构性恒零字段、恒真的 `wait_legal`，以及 3 个可由其他字段精确推出的别名。

删除项包括 WAIT/BOMB 下没有意义的目标距离变化、WAIT/BOMB 的返回与周期字段、部分炸箱目标字段、部分跟踪对手字段，以及 `can_drop_bomb`、`escape_after_bomb` 等精确重复量。`own_bomb_pending` 被刻意保留，因为它来自时序状态，可能与框架的放弹可用标志发生有诊断价值的偏离。

因此 v9 的设计目标是降低输入维数与冗余，而不是改变可表达信息。迁移必须按 `KEEP_INDICES` 投影权重，不能简单截取前 139 列。

### 4.10 v10：从 v7 分叉的 8 维象限密度实验

正式 ID 是 `continuous-v10-agent-quadrant-density`。它没有继承 v8/v9，而是在 v7 的 162 维后增加 NW/NE/SW/SE 四象限的箱子密度和对手密度，共 8 维。

象限以 Agent 当前坐标为中心；恰好与 Agent 同 x 或 y 的格子按 0.5/0.5 分摊到两侧。箱子密度的分母是对应象限的非石墙容量，对手也用相同容量归一化。这样表达的是局部方向上的“占用密度”，但它不考虑可达性：墙后箱子也会计入。

### 4.11 v11：从 v7 分叉的 8 维可达箱子目标实验

正式 ID 是 `continuous-v11-agent-quadrant-crate-objectives`。它用更任务相关的可达性替换 v10 的原始密度：

- 四象限 `reachable_crate_*_share`：该象限可达箱子数占全部可达箱子的份额；
- 四象限 `nearest_crate_*_distance`：到该象限最近可达箱子前沿的 BFS 距离；无目标记为 1。

每个箱子只有至少一个相邻、非阻塞且从 Agent 可达的前沿格时才计入。位于象限边界的目标仍按权重分摊。v11 因而比 v10 更关注“实际可完成的区域目标”，但不包含 v8 的安全炸箱交互，也没有采用 v9 的压缩。

## 5. 迁移与兼容性结论

- 维数改变意味着第一层网络权重形状改变；普通 resume 应拒绝跨版本恢复。
- 尾部追加的版本可采用显式迁移：复制父版本输入列、新列置零，同时按实验契约重置 optimizer/replay。仓库中的迁移脚本正是用于这种受控 transfer，而不是假装 exact resume。
- v3 改变了旧字段的数值尺度，v9 改变了字段索引，二者尤其不能仅靠补零处理。
- v10/v11 是竞争性分支，不能写成“v11 在 v10 上再增加”。两者同为 170 维也不代表 checkpoint 兼容，因为字段含义完全不同。
- 判断一个模型使用哪个 v，必须读取 checkpoint/config 的完整 `feature_id` 和 schema，不能只看 Agent 目录名。
